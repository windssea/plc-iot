# PLCnext Python IoT 边缘采集网关项目架构设计方案

**版本：V1.0**
**目标平台：Phoenix Contact PLCnext 系列**
**边缘运行环境：Python + Linux / OCI Container**
**北向协议：MQTT**
**南向首期协议：Modbus TCP、OPC UA、MQTT**
**扩展协议：Modbus RTU、S7、BACnet、EtherNet/IP、IEC 104 等**

本文是立项时的需求与方案草稿。已收敛的决策见 [初始技术设计](初始技术设计.md)；当前实现范围见仓库 README。南向 MQTT 仍未实现，OPC UA 已按只读订阅落地。

---

# 1. 项目背景

现有系统已经具备 IoT 平台，需要在 Phoenix Contact PLCnext 控制器上增加一个通用工业数据采集程序，使 PLCnext 同时具备 PLC 控制器和工业边缘网关能力。

IoT 平台负责配置：

* 网关
* 设备
* 设备 IP
* 通信协议
* 通信参数
* 点位
* 数据类型
* 采集频率
* 数据转换参数
* 上报策略

平台通过 MQTT 将配置动态下发至 PLCnext。

PLCnext 上运行 Python Edge Agent，根据平台下发配置动态创建协议连接、采集任务和点位映射，并将采集数据统一转换后通过 MQTT 上传到 IoT 平台。

PLCnext 的 ST/FBD 控制程序不承担通用 IoT 数据采集任务。

对于确实需要参与 PLC 控制逻辑的少量关键数据，可以通过 PLCnext gRPC/GDS 与 PLC Runtime 交换。

PLCnext 官方架构本身基于开放 Linux，同时支持 Runtime 内程序和 Linux 非控制程序运行；GDS 用于不同程序、现场总线以及系统组件间的一致数据交换。

# 2. 项目目标

本项目最终形成一个运行在 PLCnext 上的标准化 Edge Agent。

整体数据流：

```text
IoT Platform
      │
      │ MQTT
      │ 配置 / 命令
      ▼
┌─────────────────────────────┐
│ PLCnext                     │
│                             │
│ Python Edge Agent           │
│                             │
│  Config Manager             │
│        │                    │
│  Device Manager             │
│        │                    │
│  Protocol Drivers           │
│  ├─ Modbus TCP              │
│  ├─ OPC UA                  │
│  ├─ MQTT                    │
│  └─ Future Drivers          │
│        │                    │
│  Point Engine               │
│        │                    │
│  Data Cache                 │
│        │                    │
│  MQTT Publisher             │
│        │                    │
│        ├───────────────┐    │
│        │               │    │
│      MQTT          gRPC/GDS │
│        │               │    │
└────────┼───────────────┼────┘
         │               │
         ▼               ▼
     IoT平台       PLC Runtime
                  ST/FBD控制程序
```

核心目标：

1. 平台动态配置，无需修改 PLC 程序。
2. 一个 Agent 支持多种工业协议。
3. 支持多设备、多点位、多采集周期。
4. 点位统一数据模型。
5. 支持动态增加、修改、删除设备。
6. 支持设备断线自动恢复。
7. 支持 MQTT 断线缓存和恢复上传。
8. 配置具备版本机制。
9. 配置错误不能导致现有采集停止。
10. Agent 异常不能影响 PLC Runtime 的控制任务。
11. 后续可以快速扩展新的工业协议。
12. 支持远程诊断和版本升级。

# 3. 项目边界

## 3.1 IoT 平台负责

IoT 平台作为整个系统的 **Configuration Source of Truth**。

负责：

```text
Gateway管理
Device管理
Point管理
协议配置
MQTT配置
采集周期配置
数据转换配置
配置版本
配置下发
配置状态管理
设备状态展示
采集数据接收
报警/日志展示
Agent版本管理
```

原则：

> PLC 上不再维护第二套人工点表。

所有业务配置最终来源于 IoT 平台。

# 4. PLCnext 负责

PLCnext 分成两个逻辑区域。

## 4.1 Linux / Python Edge 层

负责：

```text
IoT连接
配置管理
Modbus
OPC UA
MQTT
设备连接
点位采集
数据解析
数据转换
缓存
MQTT上报
设备诊断
Agent升级
```

## 4.2 PLC Runtime

负责：

```text
IO
实时控制
联锁
状态机
运动/设备控制
实时报警
PLC周期任务
```

Python 与 PLC Runtime 采用 **弱耦合架构**。

即使：

```text
Python异常
Python重启
MQTT断开
IoT平台离线
```

也不应该影响 PLC 原有实时控制。

# 5. Python 与 PLC Runtime 的关系

默认情况下：

```text
工业设备
   ↓
Python
   ↓
MQTT
   ↓
IoT平台
```

PLC Runtime 不参与。

只有需要参与控制的关键点才进入 Runtime：

```text
工业设备
   ↓
Python
   ↓
gRPC / GDS
   ↓
PLC变量
   ↓
ST控制
```

例如总共有：

```text
5000个采集点
```

但实际 PLC 控制只需要：

```text
50个点
```

则：

```text
5000点 → MQTT上报
50点   → 同步PLC Runtime
```

不建议为了“PLC 对接”把所有 IoT 点都写进 PLC Runtime。

当前 PLCnext 已有 Python 通过 gRPC 访问 PLCnext Engineer 工程变量的实际实现，2026 年的示例覆盖 AXC F 2152 和 AXC F 3152；具体依赖安装方式会因控制器架构不同而变化。

# 8. Agent 进程模型

整个 Agent 推荐使用单进程 asyncio 模型。

```text
Python Process
│
├── MQTT Config Task
│
├── Config Apply Task
│
├── Device 001 Task
├── Device 002 Task
├── Device 003 Task
│
├── OPC UA Subscription Task
│
├── MQTT Device Subscriber
│
├── Report Task
│
├── Offline Queue Task
│
├── Health Task
│
├── PLC Bridge Task
│
└── Log/Metrics Task
```

重点原则：

> 不允许一个设备通信超时阻塞其他设备。

例如 Device01 Modbus 超时 3 秒：

```text
Device01 → timeout
```

不能导致：

```text
Device02
Device03
Device04
```

暂停 3 秒。

因此网络 IO 应采用异步实现。

# 14. Modbus 地址优化

不能一个 Point 一个 Modbus 请求。

例如点位：

```text
40001
40002
40003
40010
40011
40012
```

应该生成采集计划：

```text
40001 ─┐
40002  │
40003  │
       ├→ Read 40001~40012
40010  │
40011  │
40012 ─┘
```

然后在本地拆包。

需要实现：

```text
AddressOptimizer
```

输入：

```text
Point[]
```

输出：

```text
ReadBlock[]
```

ReadBlock：

```text
Area
StartAddress
Quantity
PointMappings[]
```

还需要限制：

```text
最大连续寄存器数量
最大地址间隔
不同pollInterval不能随意合并
```

# 15. OPC UA 配置模型

例如：

```json
{
  "deviceId": "plc-001",
  "protocol": "opcua",

  "connection": {
    "endpoint": "opc.tcp://192.168.10.102:4840",
    "securityPolicy": "Basic256Sha256",
    "securityMode": "SignAndEncrypt",
    "username": "iot_client",
    "credentialRef": "cred-001"
  },

  "points": [
    {
      "pointId": "temperature",
      "nodeId": "ns=3;s=Machine.Temperature",
      "dataType": "float",
      "samplingInterval": 1000,
      "deadband": 0.1
    }
  ]
}
```

OPC UA 推荐：

```text
Connection
    ↓
Session
    ↓
Subscription
    ↓
MonitoredItem
```

而不是简单：

```text
while True:
    read_node()
```

PLCnext 自身的 OPC UA 实现也支持 subscription/sampling 模型，其 Runtime 变量能够通过 OPC UA 暴露；变量可选择只开放标记的对象，以减少负载和通信量。

# 16. MQTT 南向设备模型

注意区分：

```text
Northbound MQTT
PLC ↔ IoT平台

Southbound MQTT
PLC ↔ MQTT设备
```

南向 MQTT 配置：

```json
{
  "deviceId": "sensor-gw-001",
  "protocol": "mqtt",

  "connection": {
    "host": "192.168.10.103",
    "port": 1883,
    "clientId": "plc-gw-001-south"
  },

  "points": [
    {
      "pointId": "temperature",
      "topic": "sensor/001/data",
      "jsonPath": "$.temperature",
      "dataType": "float"
    },

    {
      "pointId": "humidity",
      "topic": "sensor/001/data",
      "jsonPath": "$.humidity",
      "dataType": "float"
    }
  ]
}
```

运行模型：

```text
MQTT Subscribe
       ↓
on_message()
       ↓
JSON Parser
       ↓
Topic Matcher
       ↓
JSONPath
       ↓
PointValue
```

MQTT 设备没有传统意义上的：

```text
pollInterval
```

应使用：

```text
message driven
```

# 21. 数据转换

采集原始值：

```text
RAW
```

经过：

```text
decode
   ↓
byteOrder
   ↓
wordOrder
   ↓
dataType
   ↓
scale
   ↓
offset
```

转换公式：

```text
engineeringValue =
rawValue × scale + offset
```

例如：

```text
raw = 2206
scale = 0.1

value = 220.6 V
```

# 22. 采集频率与上报频率分离

这是架构的重要原则。

例如：

```text
采集周期 = 100ms
上报周期 = 1000ms
```

代表：

```text
设备
 │
 ├─100ms读取
 ├─100ms读取
 ├─100ms读取
 │
 ▼
LatestValueCache
 │
 │ 1秒
 ▼
MQTT Batch
```

不能将：

```text
pollInterval
```

直接理解成：

```text
MQTT publishInterval
```

# 23. ReportMode

建议支持：

```text
cyclic
change
change_or_cyclic
```

### cyclic

例如：

```text
每5秒上传一次
```

### change

只有：

```text
abs(new-old) > deadband
```

才上传。

### change_or_cyclic

值变化立即上报，同时保证一定时间至少上报一次。

工业场景推荐：

```text
change_or_cyclic
```

# 25. 配置下发模型

平台推荐下发 **完整快照** 为主。

```json
{
  "messageId": "msg-10001",

  "gatewayId": "GW-001",

  "configVersion": 105,

  "timestamp": 1788748123123,

  "devices": [
    {}
  ],

  "report": {}
}
```

第一阶段不要急于实现复杂 Patch。

优先：

```text
Full Snapshot
```

原因：

```text
容易恢复
容易审计
容易做版本比较
不容易出现状态漂移
```

以后配置特别大时再增加：

```text
Delta Config
```

# 26. 配置处理事务

绝对不能：

```text
收到JSON
  ↓
立刻删除当前配置
  ↓
创建新配置
```

正确流程：

```text
MQTT Receive
      │
      ▼
JSON Decode
      │
      ▼
Schema Validate
      │
      ▼
Semantic Validate
      │
      ▼
Version Check
      │
      ▼
Build Candidate Config
      │
      ▼
Calculate Diff
      │
      ▼
Preflight
      │
      ▼
Apply Candidate
      │
   ┌──┴───┐
Success  Failure
 │         │
 ▼         ▼
Commit   Rollback
 │         │
 ▼         ▼
ACK OK   ACK ERROR
```

原则：

> 新配置失败，旧配置继续工作。

# 29. 数据上报

不建议：

```text
一个Point = 一条MQTT消息
```

# 37. Offline Queue 策略

必须设容量限制。

例如：

```text

```

或者：


```text
Drop Oldest
```


事件。

# 72. 系统设计原则总结

整个项目坚持七个原则。

### 1. Platform Driven

配置全部来自 IoT 平台。

### 2. Configuration Driven

Python 不知道现场具体有什么设备。

程序只认识：

```text
DeviceConfig
PointConfig
```

### 3. Driver Plugin

协议驱动可以不断增加。

### 4. Async First

网络通信异步化。

### 5. Runtime Isolation

Python IoT Agent 与 PLC Runtime 解耦。

### 6. Fail Safe

新配置失败不影响 LastGoodConfig。

### 7. Observable

所有 Gateway / Device / Point 都应该能诊断。

系统职责：

```text

配置中心
设备管理
点位管理
数据中心
运维中心

Python Edge Agent
=
协议采集引擎
数据处理引擎
边缘通信Agent

PLC Runtime
=
实时控制系统
```

三者职责清晰，不互相替代。

这是比：

```text

+
巨大Node-RED Flow
```

或者：

```text
IoT平台
+
巨大ST程序
```

更适合长期产品化、批量部署和协议扩展的架构。
