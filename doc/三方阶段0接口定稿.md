# Python IoT 阶段 0 共同规范入口

版本 `HUB-IOT-PLC-P0/2`，2026-10-24。设计定稿，未实现或运行验收。唯一规范位于同工作区的[三方接口与验收定稿](../../PLCnext-Engineer/docs/阶段0-三方接口与验收定稿.md)，不在本仓库复制一套字段或策略。

后续按共同 TimeProvider/timeSyncV1 接入采样与报文，按 reportPolicyV1 对齐名义轮询周期、FIRST/质量变化、deadband、pending shadow 和真实所有权；不能继续在 Outbox 有空时从 latest 重建已选历史，也不能把有意过滤混成丢样。

P0/2 要求首次控制经 CONTROL_SEND 独立提交、DATA 经 SEND 放行；报告网格来自调度计划，周期游标不因接纳失败停留。STALE 按最近最终结果的活性判断，旧提交/ACK 不回退最新报告基准。已接纳 RAM/FIFO 在时间失效后保留历史所有权，恢复用新任务令牌物化，未接纳的无效样本不能补时。16 项 Total 为已知下界，未知 gauge/缺口数量用 null；诊断须取得同一逻辑所有权快照。

当前 SampleBuffer 溢出、latest 合并、outbox.dropped 拒绝尝试及 created/next_due 的墙钟行为是已核对的实现差距。新增 16 项 Total、快照及 bufferDiagnosticsV1 时保留旧 heartbeat 字段语义；按共同定义处理未知/旧记录，不把旧批次字段反推成完整采样身份。SQLite 的 64 MiB 是 payload 配额，不是 DB/WAL/索引物理总量；新格式迁移及元数据/磁盘预算属于后续实现。

SQLite Outbox 继续保护已提交的原 payload；入队重试与首次接纳失败分开，仍由上游 FIFO 持有时属于待处理，不重复报损失。跨重启年龄、单调退避、迟到 STORED 和终态竞争按[授时方案](../../PLCnext-Engineer/docs/MQTT平台授时方案.md)及共同规范执行。

本次仅完善文档入口，未修改 Python、SQLite、共享 Schema/Topic 或运行 Agent。未来实施须使用共同 R01～R14/T01～T06 样例及 A01～A16，通过旧 Agent 共存、持久化故障和真实 Hub 回执闭环后才能放行。

阶段 1 的 I01～I06 任务及依赖见[S1-PLAN/2 三方阶段 1 实施计划](../../PLCnext-Engineer/docs/阶段1-三方实施任务与顺序.md)：先入口事件/报告规则，再拆开入口与慢 SQLite 提交的阻塞链，落实有界 FIFO/所有权/计数、单调等待与重连退避，再做批次调度与既有 payload 恢复回归。若提前平台授时，所有存储入口的时间保护及其必需迁移也前移；同运行期终态对账是阶段 1 必需项，完整跨重启新增关联未实现的范围单列，不以原 payload 可恢复代替全链路计数已完整。
