## I05：统一累计事实与逻辑快照

[Accounting](../../src/plcnext_iot/reporting/accounting.py) 由 ProcessBootContext 持有，采集、资格决定、物化、SQL 提交、终止和 ACK 确认在各自明确边界发布事实。同进程重连、配置变化及本地设置重载保留同一 counterEpoch/16 项 Total，新进程使用新 boot；不将旧 meta.dropped/dead_pruned 导入当前 Total。计数字段与 H05 共同参考逐项比对，安全整数上限饱和后设置 counterOverflow=true，当前 epoch 的 accountingComplete 不自行恢复为 true。

| 实际边界 | 本地统一行为 |
|---|---|
| 不可变事件创建 | captured 增一次，进入 decisionPending；同点相邻 PHYSICAL_RESULT 的原始非 null UTC 相等才计 sourceTimestampRepeat，状态事件不去重/打断物理结果比较 |
| 首次资格决定 | eligible 或 policyFiltered 一次；捕获溢出、旧配置资格前弃置和无法完成决定的事件计 undecidedLost，不猜测 eligible |
| 已选但时间/容量拒收 | knownUnsent 与对应 timeInvalid/入队拒绝尝试分别按单位记录；不推进值/质量基准 |
| 后续 SQLite/工作队列拒绝 | 增 enqueueRejectedAttempts，原事件仍为 P；多次失败不重复计损失 |
| RAM→冻结→SQL→STORED | pendingEvents 按唯一逻辑所有者维护，SQL 提交不会再次增加事件数；删除事务成功后首次计 storedConfirmed |
| 本地终止/永久拒收 | knownUnsent/uncertainDelivery/isolated 按实际来源首次记录，死信修剪不重复增加终止 Total |
| 迟到 STORED | 原关联可核验时更新当前集合 U→S，增加 storedConfirmed/lateStored，保留曾 uncertain 的历史事实，不将 Total 当互斥分组直接相加 |

统一快照通过短时共享锁复制计数、gauge 和 lastGap；锁内不执行数据库/SDK I/O。SQL 执行期间 RAM 仍拥有事件，成功后发布交接；ACK 可以在报告任务完成本地引用释放前确认，但快照不会将同一事件同时计入 FIFO 和 Outbox。测试专门暂停“已提交但报告任务尚未释放 RAM 引用”的窗口，验证提交/ACK 两侧快照仍一致，慢数据库不阻塞读取诊断。

pendingEvents 覆盖已选暂存、FIFO、冻结及已提交 PENDING；decisionPending 单列，未判资格的事件不混入 E。pendingBatches 包括已经物化但尚未提交的 RAM 冻结批次，提交时只交接、不再加一次。buffer.quotaKind=`PAYLOAD_TOTAL` 的 usedBytes 仍只计 SQLite PENDING+DEAD payload；它不包含报文前 RAM，可能出现 pendingBatches>0、usedBytes=0，不能用此推导“没有积压”。原 heartbeat.queue 仍保持既有 SQL 批次/字节/拒绝尝试含义，其他旧本地统计也继续保留，统一口径以 diagnostics.counters/buffer 为准。

缺口最多保留 64 条；携带固定 reason/outcome、实际 eventCount 或 null、captureBoot/config/点位/序号/UTC 范围。范围只作索引，不把宽度当点数；没有依据时不补当前 UTC。截断不撤销 gapRecordsTotal。身份、采样结构或 payload 损坏、记录器失败、计数溢出及恢复关联未知会明确标记不完整。仍持有的损坏批次保留为 P、停止完整性声明，不伪造已知丢失或 STORED。

元数据总预算保持 4 MiB：统一诊断预留 1 MiB（待决身份、最多 2000 点的相邻 UTC 索引、计数及有界缺口），Outbox 关联/调度使用剩余 3 MiB。诊断索引达到数量/字节限额则截断并标不完整，不让缓存无限增长。业务入口、选择区和 worker 原 4/32/2 MiB 配额分别保持，不把该记账上限等同整个解释器 RSS。

v1 SQLite 恢复没有采样身份及本地终态来源：对应 pendingEvents/deadEvents 为 null，16 项 Total 只给当前 boot 已知下界；确认旧批不会把旧 boot 点数灌入新 Total。即使旧库为空，也没有新增持久字段来证明上次 RAM 完全排空，因此首次打开既有库会记录 eventCount=null 的 VOLATILE_RESTART/UNCERTAIN；同进程重复打开不会重复新增该恢复缺口。清空恢复队列后 gauge 可以重新成为已知零，当前 epoch 的不完整标记仍保留。

## 本地读取与独立记录器

[TelemetryPipeline](../../src/plcnext_iot/reporting/service.py) 的 `stats().diagnostics` 和同步 `diagnostics_snapshot()` 提供统一快照，当前实现明确附带 `timeMode=SYSTEM_RTC_COMPAT_UNVERIFIED`。本地初始化服务的 `GET /api/diagnostics/buffer` 借用当前生命周期指针读取同一快照；遥测不可用时返回 503，不新建数据库或连接设备。这个本地 API 不是已上线的 bufferDiagnosticsV1 MQTT Topic，未添加新的线上 Schema/Topic，也未替换心跳字段。

[AuditRecorder](../../src/plcnext_iot/reporting/audit.py) 是独立有界 JSONL 旁路，不取走业务 FIFO。记录捕获值/质量/原始时间与名义槽、资格结果、缺口、事件→messageId/hash、预留、SDK 接受/明确拒绝、终止及确认事实；恢复旧批只记录已知批次身份和未知事件范围，不制造 sampleSeq。

批次关联按最多 15 个 sampleSeq 分块：单个身份沿用 sampleSeq，多身份用 sampleSeqs 的十进制逗号列表与 eventCount，最大安全整数宽度也不超过 256 字符。列表逐项精确还原，不是“范围内每个序号都发生”的推断；非连续身份已做回归。这样避免每次批次状态转换都为每个值单独写一行。记录器队列默认 512 项，每条最多 8192 字节，累计最多 100000 条/64 MiB，独占新文件，关闭最多等待 2 秒。拒写、满额、异常或关闭未完成都明确返回不完整，影响最终退出结果；不以有限记录器证明任意长运行全量无损，也不提供样本日志/断电持久承诺。

`tools.agent` 和 `tools.appliance` 均增加可选 `--audit-file <新路径>`；appliance 的记录器跨同进程本地重载共用。默认不创建审计文件。下面仅说明后续使用方式，本轮没有执行启动 Agent/设备的命令：

```powershell
./.venv/Scripts/python.exe -m tools.appliance --data-directory <现有目录> --audit-file <新的JSONL文件>
```

## I06：原有开发 SQLite 与真实 Hub 回执

发现并只读核对现有 `.local/setup-preview/telemetry.db`：v1、gateway=`PLC-UI-DEMO`、批次表为空、完整性检查正常，应用锁可用。使用这个原文件执行验证，未创建/复制临时 SQLite，也未创建临时 PostgreSQL；SQLite 连接包装器强制唯一批准路径和 URI mode=rw，文件不存在即拒绝，子进程同样受限。测试期间持有原开发目录的 commissioning/agent 锁，不启动采集器或配置生命周期。

[现有库恢复工具](../../tools/verify_existing_outbox.py) 在现有开发 PostgreSQL `hub` 中创建精确 ID 的测试网关、1 个子资产/点及历史配置，关闭采集，不创建采集任务。沿用现有 PID `34208` 的后端及 Broker。输入是明确标记的合成 DATA，STORED 全部来自真实 Hub；不能将测试输入当成设备采样或将注入 ACK 单元用例当成平台提交证据。

| 提交/恢复边界 | 实测结果 |
|---|---|
| enqueue 成功后进程 `os._exit(23)`，不执行正常 close | 新进程读取相同 payload、SHA-256、messageId、bootId、sequence、configVersion 和原 timestamp |
| reserve 提交后退出 | attempts 保留；新进程不使用旧 next_due/旧 monotonic，仍按新进程等待重建；测试注入单调推进以避免真实等待 60 秒 |
| 独立发布进程收到真实 STORED 后、SQLite 删除前退出 | 原批次仍为 P，下一进程按原字节恢复；没有提前以 PUBACK/曾收到 ACK 删除 |
| 重发已被 Hub 保存的原字节 | 两次真实 STORED，仅 1 份收据、1 条原始数据；收据 hash 与本地原 payload 完全相同 |
| 使用真实 STORED 完成删除事务后退出 | 新进程再次打开原库，该 messageId 不复活 |
| v1 旧关联恢复 | 当前 boot 的事件数未知、恢复缺口 eventCount=null、accountingComplete=false；不把旧批次换算成新 epoch 的采样/确认 Total |

在同一原有 SQLite 还执行了实际生产 SQL 分支：INSERT 授权拒绝回滚；仅在当前未提交视图改坏本轮 payload，验证 hash 拦截后回滚；暂时把 max_page_count 降到当前页数，触发真实 SQLITE_FULL 并验证没有部分插入；DEAD 转换后遇 DELETE 拒绝时整笔事务回滚、随后成功转换/修剪；保持 WAL 读者快照时写准入关闭。物理池与空闲空间不足的保护分支另用受控小限额/可用空间输入验证。

这些验证不填满开发磁盘，不改生产数据库格式，也没有把开发库副本改坏后恢复。未声称实测写满 256 MiB/真实磁盘掉满、COMMIT 执行中硬断电或 PLC 介质可靠性。暂用系统 RTC 的 created 七天年龄、可信 UTC/误差/时基迁移、跨进程完整采样关联仍按阶段 2/后续范围单验，不因本轮软件恢复通过而自动放行。
