# ARM / AMD64 容器镜像

> 当前版本为 **0.2.0**。默认入口是浏览器初始化（`tools.appliance`），无需现场配置文件。请先阅读[本地初始化说明](本地初始化与PLCnextApp部署.md)。下文“文件挂载运行”仅适用于 0.1.0 的 `tools.agent` 入口；不要把那套路径套到 0.2.0 Compose。

支持三个 Linux 目标：`linux/amd64`（Intel/AMD 64 位）、`linux/arm64`（AArch64）、`linux/arm/v7`（32 位 ARM hard-float）。ARMv7 与 ARM64 不可混用；在 PLC 上用 `uname -m` 确认：x86_64 → amd64，aarch64 → arm64，armv7l → arm/v7。

镜像包含 Python 3.12 和锁定依赖，目标宿主机无需安装 Python 或 systemd；宿主机须具备兼容的 Linux 内核及 Docker/Podman。基础镜像为固定多架构索引摘要的 Python 3.12.14 slim-bookworm。构建阶段在开发机架构运行，按目标架构安装 manylinux wheel，最终镜像不运行跨架构构建命令，因此构建不依赖 QEMU。若将来某项依赖没有目标 wheel，构建直接失败，不回退到安装开发机二进制。

## 构建与离线包

在项目根目录执行：

```powershell
./.venv/Scripts/python.exe -m tools.build_images --image plcnext-iot:0.2.0 --output .local/images/new-build
```

默认生成三个独立 Docker archive：`plcnext-iot-amd64.tar`、`plcnext-iot-arm64.tar`、`plcnext-iot-armv7.tar`，内部标签分别为 `plcnext-iot:0.2.0-amd64`、`plcnext-iot:0.2.0-arm64`、`plcnext-iot:0.2.0-armv7`。输出文件已存在时拒绝覆盖；构建失败可能留下未完整的归档，重试使用新输出目录。当前镜像产物位于 `.local/images/0.2.0/`。0.1.0 归档仍可作对照，不能当作当前入口。

只构建部分架构可传 `--platforms linux/amd64,linux/arm64`。`--mode load` 将各架构镜像载入本机引擎；默认 archive 不推送仓库。构建脚本使用独立参数列表调用 Docker，支持 Windows PowerShell 和 Linux。

将匹配目标架构的 tar 传到设备后：

```sh
docker load -i plcnext-iot-arm64.tar
# Podman 用户使用 podman load -i plcnext-iot-arm64.tar
```

需要统一标签的多架构仓库镜像时，先登录自己的仓库，再显式执行：

```sh
python -m tools.build_images --image registry.example.com/team/plcnext-iot:0.2.0 --mode push
```

该命令会向指定仓库发布一个包含三种架构的索引，拉取时按设备架构选择。当前工作未推送仓库。若当前 builder 不支持多平台导出，可创建独立 docker-container builder，并传 `--builder 名称`，不必修改全局默认 builder。参见 [Docker 多平台构建说明](https://docs.docker.com/build/building/multi-platform/)。

## 配置和运行

0.2.0 镜像不包含 PLC 身份、Broker 密码或现场采集配置。持久数据在 `/var/lib/plcnext-iot`。首次访问 `http://设备IP:8080` 完成初始化；采集驱动为 `all`（Modbus TCP 与 OPC UA）。OPC UA 用户名写在业务快照里，密码若使用 `passwordEnv`，必须由容器运行环境提供同名变量，初始化页不会代填南向凭据。

0.1.0 文件挂载入口使用以下路径（仅旧镜像）：

- `/etc/plcnext-iot/bootstrap.json`、`mqtt.json`：只读配置挂载。
- `/var/lib/plcnext-iot`：持久数据卷，保存配置数据库和遥测 Outbox。
- 环境变量 `IOT_MQTT_PASSWORD`：由外部环境文件提供，mqtt.json 的 passwordEnv 引用它。

复制 `deploy/linux/bootstrap.json` 和 `mqtt.json` 到 `deploy/container/config/`，修改 gatewayId、Broker 和用户名。bootstrap 中 dataDirectory 保持 `/var/lib/plcnext-iot`；私有 CA 文件一同放在 config 中，mqtt.json 的 caFile 填容器内路径或相对于 mqtt.json 的路径。创建 `deploy/container/agent.env`，写入实际密码环境变量；这些现场文件已加入 Git 忽略列表和 Docker 构建上下文排除规则。

镜像使用固定 UID/GID `10001:10001`。配置文件应允许该用户读取；数据目录必须允许该用户写入。Compose 使用命名卷，Docker 首次创建卷时复制镜像目录的权限。已有卷或宿主机绑定目录需自行确认权限；rootless Podman 需按其用户映射设置权限。

```powershell
$env:IOT_IMAGE = 'plcnext-iot:0.2.0-amd64'
docker compose -f deploy/container/compose.yaml up -d
docker compose -f deploy/container/compose.yaml logs --tail 100
```

ARM64 离线部署将 IOT_IMAGE 改为 `plcnext-iot:0.2.0-arm64`；ARMv7 使用对应 armv7 标签。使用仓库索引时设置统一标签即可。Compose 未固定 platform，以实际镜像和宿主机匹配为准。当前 Compose 映射 8080 供初始化页面使用。

Compose 默认只读根目录、非 root、移除 capabilities、限制日志文件大小，开放临时目录和持久数据卷。采集器主动连接 Modbus、OPC UA 和 MQTT；除初始化页外不需要其他入站端口。容器内的 localhost 指容器自身，Broker 和设备地址应使用容器可路由的实际地址。停止宽限时间 30 分钟，SIGTERM 由 Python 主进程接收。没有将数据库锁检测用作 healthcheck，避免第二进程干扰在线 Agent。

升级先停止容器并备份持久卷，再替换镜像标签，重新创建容器。保留命名卷可恢复配置与补传队列；不要使用 `docker compose down -v` 作为常规升级操作。容器回退仍需确认数据库格式兼容。

## 验证边界

```powershell
./.venv/Scripts/python.exe -m tools.inspect_image_archives .local/images/0.2.0
./.venv/Scripts/python.exe -m tools.image_smoke --image plcnext-iot:0.2.0 --platforms linux/amd64
```

三个归档均可构建。镜像现含 asyncua 及其依赖；原生扩展仍须匹配目标架构 wheel。AMD64 已运行验证原生依赖导入、非 root/只读根目录、配置应用、停止及重启恢复。当前 Docker 引擎没有 ARM 模拟能力时，ARM64 实际启动会返回 exec format error；ARM64/ARMv7 运行验收仍需对应设备或启用模拟的测试环境。支持模拟时可省略 image_smoke 的 platforms 参数运行全部架构。ARM 真机上应额外验收实际设备采集、TLS、断网补传和资源占用。
