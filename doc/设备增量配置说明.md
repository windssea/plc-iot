# 按设备增量下发配置

Agent 在保留 `config/set` 完整快照兼容入口的基础上，支持 `config/patch` 设备命令。Hub 可以只发送选中的设备：新增使用 `add`、更新使用 `replace`、删除使用 `remove`。终端将命令与当前已提交配置合并，持久化完整快照；未涉及设备的配置保留，采集任务按现有执行键复用。

## 消息与基础版本

Topic 前缀仍为 `iot/v1/gateway/{gatewayId}/`。`config/patch` 和 `config/patch/ack` 均使用 QoS 1、`retain=false`，对应 Schema kind 为 `configPatch` 和 `configPatchAck`。终端拒绝从 Broker 重放的 retained patch，避免离线历史增量被误当作当前操作。

命令包含原信封 `schemaVersion`、`gatewayId`、`messageId`、`configVersion`、`timestamp`，以及：

| 字段 | 说明 |
|---|---|
| `baseConfigVersion` | 终端已提交的全局版本，未初始化时为 0 |
| `baseMessageId` | 该版本原始快照的 `messageId`，未初始化时为 null |
| `operations` | 0–50 项，每个设备最多一项操作；零项仅限明确修改 `gateway` |
| `operations[].op` | `add`、`replace`、`remove` |
| `operations[].deviceId` | 稳定设备标识 |
| `operations[].device` | 新增或替换必须携带完整设备及点位配置；删除不得携带 |
| `gateway` | 可选网关 `enabled` / 完整 `report` 设置 |

目标 `configVersion` 必须大于基础版本，允许跳号。非空终端同时核对基础版本和原始消息身份，任一不符返回 `BASE_CONFIG_MISMATCH`，不会自动采用 Hub 的草稿覆盖其他设备。首次 `0/null` 引导必须携带 `gateway.enabled` 和 `gateway.report`；已提交空设备列表仍属于已配置终端，不能再次使用零基础引导。

`add` 要求设备不存在，`replace/remove` 要求设备存在。重复操作、操作 ID 与设备 ID 不符、未知字段或非法点位全部拒绝。合并后重新验证完整 `configSet`，继续遵守设备最多 50、总点位最多 2000 和 2 MiB 配置消息上限。

网关启停、报告设置以及空网关首次初始化可使用 `operations: []`；此时必须携带非空 `gateway`。既没有设备操作又没有网关设置的空命令拒绝。Hub 可在预览阶段阻止设置与当前值相同的发布；终端仍按显式目标版本执行合法命令，不猜测发送方意图。

## 提交、重发与确认

命令经过现有串行 actor 队列和专用配置存储工作线程，执行 prepare → 采集任务切换 → commit → 同一事件循环内 publish。提交失败恢复原配置；驱动启动失败停止候选并恢复旧任务。未选中设备保持原任务实例，不重新连接南向设备。网关启停或报告参数属于明确的全局修改，不是单设备隔离承诺。

SQLite `requests` 增加可空 `command_digest` 和 `command_kind` 两列，数据库 `user_version` 仍为 1。由持有原 OS 锁的存储所有者在事务中安全增加列，已有完整快照记录保留 null 值。Web 仍只读取完整活动快照，不需要认识命令载荷。

终端保存每条 patch **原始字节 SHA-256**、原消息身份、目标版本与应用状态。处理时先查持久记录，再检查基础版本。完全一致且曾提交成功的重发，即使终端已应用更高版本或重启，也确认其曾成功，保持当前运行配置。相同 `messageId` 换字节、版本或消息种类返回冲突。不得为了重试重新生成时间戳、消息 ID 或格式化 JSON。

Patch ACK 明确区分曾应用与当前活动状态：

| 字段 | 说明 |
|---|---|
| `configVersion` / `messageId` | 原命令目标版本与身份 |
| `appliedConfigVersion` | APPLIED 时等于原目标版本；REJECTED/FAILED 时为 null |
| `activeConfigVersion` | 当前终端已提交版本，可高于历史重发目标 |
| `activeMessageId` | 当前版本原始快照身份；零版本为 null |
| `status` / `errors` | 原状态枚举和有界脱敏错误；APPLIED 无错误 |

旧 `config/ack` 的 APPLIED 仍要求目标版本等于活动版本，原语义不变。提交结果未知时不猜测 ACK 中的版本或身份。

连接后的 `config/get` 及原每 30 秒 GET 增加可选 `configCapabilities: ["devicePatchV1"]` 和 `activeMessageId`。能力为静态常量，身份读取现有生命周期指针；不为此增加数据库查询或后台缓存。Patch ACK 后再发送一次 GET，供 Hub 对账。旧 GET 不包含新字段仍合法；Hub 应先确认能力与实际基础，再发送增量。

## 迁移及性能边界

完整 `config/set` 仍是兼容入口。Patch 后 Broker 中较低版本的旧 retained 完整快照会被版本保护拒绝，不能回滚。首次空终端连接时可能先收到已有 retained 完整快照，因此不能假定新设备必然是零基础；发送端必须读取 GET 并按实际基础发布。清理旧 retained 配置应由部署方明确安排，不由 Agent 擅自删除 Broker 数据。

本功能没有新增采样缓存、每点回调、遥测队列、线程或常驻任务。合并、全量静态校验和 SHA 只发生在配置命令到达时，沿用已有配置工作线程与资源上限；采样、报告及 Outbox 热路径不变。设备任务复用仍使用已有执行键，改报告名称/策略不需要重连。所有设备仍共享全局配置版本，后续采样使用新版本，不能给旧版本样本改标签。

各消息种类的校验器共享同一份协议 Schema 定义，首次加载和 Schema 自校验只执行一次。冷启动时的并发加载由短锁保护，后续报文校验仍各自执行；增加 patch 种类不会为每种消息再复制整份 Schema。

本地离线验证覆盖结构与跨字段语义、旧数据库升级、三种操作、合并后上限、exact-wire 重放、重启恢复、并发基础竞争、驱动/存储回滚、未选中任务身份、MQTT 独立 ACK / GET 顺序和 retained patch 拒绝。服务联调及终端资源实测由 Hub 演示阶段另行验证。
